# בידול MaintainOS — מקור אמת להחלטות

**סטטוס:** קנוני · חל על כל החלטת מוצר, עיצוב, ארכיטקטורה ופיתוח  
**Optical Center** = דייר ראשון / פיילוט; לא הגדרת המוצר.

---

## מי אנחנו

**MaintainOS** היא מערכת הפעלה תפעולית לרשתות מרובות סניפים.

המטרה: לאפשר להנהלת הרשת להבין **למה** תקלות מתרחשות, **מה העלות האמיתית** שלהן, ו**אילו פעולות ימנעו** את התקלה הבאה — על בסיס ליבה אחידה ו־Digital Twin תפעולי לכל סניף.

## מי אנחנו לא

| לא | למה |
|----|-----|
| עוד מערכת Ticketing | טיקט הוא אמצעי, לא המוצר |
| פרויקט מותאם ידנית לכל לקוח | ליבה אחת; התאמה רק בממדים המותרים |
| CMMS גנרי / מלאי מלא | לא בונים מודולי תחזוקה שאינם מזינים Twin או תובנות רשת |
| Marketplace לטכנאים | ספקים הם שכבת ביצוע אופציונלית, לא הליבה |

---

## ליבה אחידה (רשימה סגורה)

כל רשת מקבלת את אותה ליבה. אין forks ללקוח.

1. **דיווח תקלה** — WhatsApp / web / QR·NFC
2. **זיהוי סניף** — קוד / QR / NFC / טלפון חנות
3. **SLA** — חלונות תגובה וסגירה + הסלמה
4. **שיוך טכנאי** — פנימי + התראות
5. **ניהול ספקים** — שיגור חיצוני כשצריך
6. **אישור סגירה** — מחזור תקלה עד closed
7. **דוחות הנהלה** — ייצוא, snapshots, KPIs תפעוליים

## משתנה בין רשתות בלבד

| ממד | דוגמה |
|-----|--------|
| מיתוג | שם, צבעי tenant, לוגו |
| הרשאות | מיפוי תפקידים / scopes |
| סוגי תקלות | קטגוריות / טקסונומיה |
| SLA | שעות respond/resolve לפי עדיפות |

כל דבר אחר — ליבה משותפת או דחייה.

## Digital Twin תפעולי (north star)

לכל סניף נבנה בהדרגה תאום דיגיטלי תפעולי שכולל:

- ציוד ומערכות
- היסטוריית תקלות
- ספקים מקושרים
- עלויות (עבודה / חלקים / שיגור)
- תדירות כשלים

**מצב נוכחי:** assets כמלאי דק מקושר לטיקטים — בסיס ל־Twin, לא Twin מלא.

### אבולוציה (אחרי יציבות ליבה / go-live)

1. **העשרת Twin** — ציוד, עלויות, תדירות כשל ברמת סניף
2. **דפוסים בין־סניפיים** — ציוד בעייתי, recurrence ברמת רשת/אזור
3. **חיזוי והמלצות** — הוצאות צפויות + תחזוקה מונעת

שכבת intelligence זו היא **post-core** — לא מחליפה את מחזור הדיווח→סגירה בפיילוט.

---

## יתרון הנהלה (מדד הצלחה)

פיצ׳ר / מסך / דוח מצליח רק אם מחזק לפחות אחד:

1. **שורש** — למה התקלה קורה (לא רק כמה טיקטים)
2. **עלות אמיתית** — מה שילמנו / נשלם
3. **מניעה** — מה יקטין את התקלה הבאה

---

## פילטר החלטה

לפני כל פיצ׳ר חדש:

```
רעיון → מחזק בידול?
         ├─ לא → דחייה / defer
         └─ כן → באיזו שכבה?
                   ├─ SharedCore          — קוד/סכמה לכל הרשתות
                   ├─ TenantConfigOnly    — מיתוג / הרשאות / סוגי תקלות / SLA
                   ├─ StoreDigitalTwin    — נתוני סניף שמזינים את התאום
                   └─ NetworkIntelligence — דפוסים / חיזוי / מניעה
```

### כללי מימוש

- **Shared core** — מימוש אחד; אין העתקת מסכים ללקוח
- **Tenant config** — רק ארבעת הממדים למעלה
- **אין** מסכי ticketing גנריים שלא מזינים Twin או דוחות שורש־עלות
- **אין** אינטגרציות outbound כלליות (Zapier וכו׳) כתחליף לליבה

### דוגמאות לדחייה

| רעיון | סיבה |
|-------|------|
| Kanban גנרי בלי הקשר סניף/SLA | ticketing בלי בידול |
| Custom workflow per client בקוד | שבירת ליבה אחידה |
| מלאי חלקים מלא בלי קישור לעלות תקלה | CMMS גנרי |
| Chat פנימי בין משתמשים | לא מחזק שורש/עלות/מניעה |
